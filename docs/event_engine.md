# First-Class Event Engine Specification & Architecture

## Overview
The **Event Engine** serves as the canonical event streaming, sequence ordering, persistence, replay, and playback navigation system for the **AI-Assisted Interactive Hadoop Execution & Learning Simulator**.

It acts as the authoritative bridge between **Deterministic HDFS Simulation** (Level 3) and **Future Dynamic Visualization** (Level 5+).

```
HDFS Simulation Engine
        │
        ▼
   Event Engine (Append-Only, Monotonic Sequence)
        │
        ▼
  Ordered Event Stream (Session-Isolated SQLite)
        ├──► Event Applier ──────► Session State (Live / Replay)
        └──► Playback Cursor ────► Future Visualization / AI Layer
```

---

## Key Principles & Architectural Guarantees

### 1. Single Canonical Event Model (`app.models.event.Event`)
All application actions—whether Session management, Conversation messages, HDFS cluster events, or Checkpoint operations—are recorded using a single, unified schema:
- `event_id`: Unique identifier (e.g. `evt_...`).
- `session_id`: Unique session binding.
- `category`: `EventCategory` enum (`SESSION`, `CONVERSATION`, `SIMULATION`, `HDFS`, `VISUALIZATION`, `VOICE`, `LEARNING`, `SYSTEM`).
- `event_type`: Specific event string.
- `sequence_number`: Monotonically increasing per-session sequence integer starting at `1`.
- `logical_timestamp`: Float timestamp from simulation clock.
- `state_version`: State version at time of event emission.
- `payload`: Structured JSON facts about what happened (no UI animation instructions).

### 2. Per-Session Monotonic Sequence Numbers & Immutability
- Sequence numbers start at `1` for each session and increment without gaps (`1, 2, 3, 4...`).
- Session A and Session B possess independent sequence streams.
- Database constraint `UNIQUE(session_id, sequence_number)` on `EventModel` guarantees sequence integrity and concurrency safety.
- Once persisted, events are immutable and append-only.

### 3. Separation of Live State vs. Replay State
- **Live Session State**: Represents the active simulation engine state.
- **Replay State**: Reconstructed historical state generated by `EventReplayer` (`replay_events` or `replay_from_checkpoint`).
- Replaying events to inspect sequence #20 does NOT mutate or corrupt live session state at sequence #50.

### 4. Requirement 45 Pause/Resume Foundation
- When playback is paused at Event sequence $N$ (e.g. #43), `EventCursor.current_sequence` remains `#43`.
- User can ask follow-up questions, and the AI layer receives the exact state corresponding to sequence #43.
- When the user says "continue", playback resumes from Event sequence #44 without restarting the simulation, regenerating events 1–43, creating duplicates, or mutating history.

## Timeline & Replay API Endpoints (`/api/v1/sessions/...`)
- `GET /{session_id}/events`: Fetch all session events ordered by `sequence_number`.
- `GET /{session_id}/events/range?start_seq=1&end_seq=10`: Query sequence ranges.
- `GET /{session_id}/events/type/{event_type}`: Query events by type.
- `GET /{session_id}/timeline`: Retrieve structured timeline response.
- `GET /{session_id}/cursor`: Fetch current playback cursor position.
- `POST /{session_id}/cursor/pause`: Pause playback at current sequence.
- `POST /{session_id}/cursor/resume`: Resume playback from next sequence.
- `POST /{session_id}/cursor/restart`: Reset cursor to sequence 0.
- `POST /{session_id}/replay`: Replay events / checkpoint to inspect historical state.
